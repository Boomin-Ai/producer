01 · The design

Control and media take separate routes.

Cloudflare hosts the application API. Postgres owns durable room permissions. LiveKit forwards the audio/video tracks. The host’s computer composes the show in OBS.

Media / show outputAuthority / cleanup requests

Guest client

The hosted web page owns camera/mic preview and the browser LiveKit connection. It publishes only allowed tracks and subscribes only to permitted sources.

Host client

Tauri’s Rust side owns the SDK and media workers. The webview issues room controls; provider credentials and the native SDK connection remain outside it.

Hosted authority

The API and database decide admission, stage membership, grants, ownership, and identity generations. A provider token does not replace those checks.

What “worker” means here: the Cloudflare Worker serves control requests; the retirement Durable Object schedules cleanup. Native Rust tasks process media on the host computer. This drawing does not imply a separate deployed cloud compositor or media-processing fleet.
02 · Guest lifecycle

Admitted, connected, and on stage are different states.

Resolve transport capability

Producer authenticates to the configured Boomin endpoint and reads the room’s RTC capability. Native LiveKit requires a compatible build; Apple Silicon 0.4.70 includes it.

Establish the host owner

Rust opens a connection ticket, starts or safely recovers the owned run, and obtains a short-lived provider session bound to that run and host epoch.

Connect and authorize incoming media

The native SDK joins LiveKit with automatic subscription disabled. An independent API read provides the allowed guest identities and sources.

Start return publication and maintain authority

Producer publishes composed program video and a host/media-only audio bus. The owner renews its host lease and polls media permissions separately.

Open invite and preview devices

The guest page captures local preview after permission. A local preview is not proof of a connected host. A persisted join intent permits retrying the same guest entry instead of creating duplicates.

Wait for admission

The API verifies the invite and creates or resumes the participant. Waiting does not authorize publishing a backstage camera to the host.

Admission unlocks the backstage media path

The host’s Admit command commits current admission authority. The live guest owner detects current admission and uses the combined startup endpoint to obtain authority, a connection ticket and a provider session in one request. Server reservation/finalization fences remain in force.

Connect, recheck, then publish

The browser connects to LiveKit, checks that its provider identity matches, then rereads authority after connection. Only current camera/mic grants are published. Camera permission is restricted to the current host.

Native host receives and renders

The native host must independently permit the identity, subscribe, receive and decode frames, schedule them, and deliver them to its native scene/thumbnail path. This is the additional path a plain browser call does not have.

Show assigns a guest to an existing slot

Scene placement and server stage membership must agree. A guest slot is needed. An already-connected backstage feed can be placed without a new camera publication.

Stage membership enables conversation and program audio

Authorized on-stage guests exchange microphone tracks through LiveKit. Native incoming guest PCM reaches the show only when current authority says on stage.

Hide preserves backstage preview

The media connection may stay warm. Broadcast placement is removed, incoming audio is gated out of program, and browser peer-audio permissions narrow on the next authorized update.

Remove revokes admission and retires the participant

Database authority changes first. Clients invalidate playback/delivery, and the durable retirement path removes provider access. This is stronger than merely hiding a tile.

Compatibility boundary: production offers native RTC capability to hosted rooms. Once a native host adopts a room, guest routing remains tied to that room’s LiveKit run history. This does not mean old or unsupported clients silently gain the native runtime. Self-hosted legacy setups are outside this path.
03 · Who hears whom

Two audio feeds form the conversation.

Live · hosted browser

Other guests’ microphones

Guest A mic→LiveKit→Guest B playback

Both must be authorized on stage. The publisher allows only its microphone track to other authorized listeners. The receiver permits only listed peer microphone identities. A guest never subscribes to its own identity. Peer cameras remain restricted to the host.

OBS bus 1→Native publisher→LiveKit → guests

This bus excludes remote guest voices. Guests receive the host/media audio here and the other guests separately, avoiding a second delayed copy of those same guest voices.

04 · Inside Producer

A browser feed becomes a native scene source.

LiveKit remote track→Authorized subscription→Decode + sender timing→Bounded queues / scheduling→Native ingest source→OBS scene / thumbnail / output

Incoming guest path

The Rust runtime maps current participant identities to allowed sources. Media workers preserve timing, bound queues, and invalidate delivery handles when permission or source ownership changes. The scene graph owns transforms, visibility, slots, and mixer routing.

A “connected” SDK room can therefore precede visible native video. First packet, first decoded frame, and first rendered thumbnail are separate milestones.

Outgoing return path

OBS program video is scaled for the guest return (1280 × 720). Bus 1 supplies host/media audio at 48 kHz. Separate capture/SDK work paths and bounded queues protect callbacks from slow consumers.

The publisher currently schedules with a 400 ms lead. This is a local return-path setting, not the total network latency or a claim about every incoming guest frame.

Streaming-platform output is a separate native output path. A 720p guest return does not imply that all audience streaming or recordings are capped at 720p.

05 · Ownership and permission

A room has one current host process.

Run + lease + epoch

A run identifies the session. A renewable lease identifies the active host process. A new epoch fences an old owner from continuing to control the room.

Revision + request ID

Mutations carry the expected run, epoch, and control revision plus a request ID. Database procedures coordinate changes and reject stale operations. An ambiguous write is not blindly repeated with a new ID.

Participant generation

Guest identities include their authorization generation. A replaced or retired participant identity cannot become valid merely by reconnecting with old metadata.

The retirement driver is necessary because changing our database does not automatically remove already-issued provider access. Durable operations coordinate participant/epoch cleanup against the pinned LiveKit project.

06 · Interruptions

Recovery creates a freshly authorized media owner.

Transport unhealthy→Stop permission reader→Retire capture + queued media→Close old SDK→Fresh authority + lease + session→Reconnect + republish

The native owner can recover under its still-valid lease using a newly created receiver. It rereads permissions after connecting and only then restarts program publication. The previous reader is joined so late responses cannot authorize the replacement connection.

What the shipped path handles

Transport failure no longer always requires manually exiting the room. Two forced SDK closes were recovered in the generated native test, and an observer-driven browser test saw the return resume after both disruptions.

What remains bounded

The native transport recovery budget is three attempts per rolling minute. Expired ownership, authority failures, teardown errors, or exhausted recovery stop the owner rather than resurrect an unauthorized session. This is not unlimited reconnect through an arbitrarily long outage.

07 · What the numbers mean

There is no single “connection speed.”

Cold join

Admit → authorized connection → first visible guest preview. Includes control, connection, publication, native reception and rendering.

Show

Show → an already-connected guest appears on stage. Backstage warming makes this much shorter than cold join.

Conversation

Speech capture → the other person’s decoded playback. This needs media markers, not just a connected event or an API stopwatch.

08 · Learning without rewriting

The experiment that separates transport from integration.

The initial architecture page proposed these controls. Subsequent generated-media tests have now run against isolated and production endpoints; see the latest results above. The complete controlled cold/warm distribution below is still unfinished.

Baseline

Browser → LiveKit → browser

Use generated camera frames and tones, automatic permissions, the same provider project and similar API path. Measure control requests, ICE establishment, publication, first packet, and first decoded video/audio.

Producer path

Browser → LiveKit → released native app

Use the same generated sender and a separate test room. Run signed 0.4.70 with verified isolated app storage. Add first native preview and outgoing return observations. A diagnostic build, if needed, must be labeled separately.

Collect a timeline, not just a pass

Admit request start/end → authority discovery → session issuance → SDK connect → publication → first received/decoded frame → native thumbnail. Use monotonic client clocks and correlated events; do not subtract unsynchronized wall clocks as if they were exact one-way latency.

Read the actual connection

Capture selected candidate path (UDP / TCP / relay), RTT, jitter, loss, bitrate, frame counts, freezes, and available decoded-audio statistics. Production detailed development phase events are disabled; use browser diagnostics and available logs first.

Repeat under controlled conditions

Start with 10 cold and 10 warm trials, preserving failures. Record hardware, network, release, region where observable, and load. Then compare one versus four guests. Report each result, median and slowest; small-sample percentiles must be labeled exploratory.

Change only after attribution

Slow API: inspect control reads and transactions. Slow ICE: inspect candidates and route. Packets arrive early but preview is late: inspect native authorization, sender timing, queues, decode and render. These findings may support targeted fixes; they do not justify a rewrite in advance.
