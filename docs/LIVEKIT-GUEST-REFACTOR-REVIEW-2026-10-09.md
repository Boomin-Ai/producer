Findings appear in severity order. Severity describes the consequence if the issue is left unresolved, rather than a claim that the proposed transport already ships.

1. **P1 — Raw audio timing and SDK queues need an explicit synchronization proof. Confirmed API limitation; bridge behavior unknown.** Plan §6, lines 99–101. At the cited upstream commit, `AudioFrame` contains PCM, sample rate, channel count and sample count, but no timestamp. `NativeAudioStream::on_data` queues only those fields. Video exposes `timestamp_us`; those two interfaces do not themselves establish a common audio/video presentation timeline. Stamping audio when an async reader wakes can turn scheduler delay into recording offset. A local sample clock can pace audio but cannot alone recover its original alignment with video.

   Correction: make G1 document the timing semantics from decode callback through OBS presentation, including how relative A/V timing is recovered or maintained. Identify a supported synchronized path or the exact upstream extension needed if the raw interface is insufficient. Count SDK queues as well as adapter queues: the inspected stream defaults to an unbounded queue with `None` or zero capacity; its bounded mode discards oldest frames on overflow. A bounded downstream queue cannot fix an unbounded upstream queue, and silent SDK drops can invalidate the bridge sample clock.

   Required proof: synchronized flash/click recording measurements, scheduler pressure, asymmetric jitter, overflow/underflow, reconnect and long-term drift. Report offset distributions and all buffering stages. Moving media and a nominally paced audio stream do not pass G1. Sources: [audio frame](https://github.com/livekit/rust-sdks/blob/35d7655c580147c2ad05fc8ffa5d885e88c822b9/libwebrtc/src/audio_frame.rs), [native audio stream](https://github.com/livekit/rust-sdks/blob/35d7655c580147c2ad05fc8ffa5d885e88c822b9/libwebrtc/src/native/audio_stream.rs).

2. **P1 — Concurrency protection must include grant mutations and admission changes. Confirmed existing source defect.** Plan §4, lines 63–69; Boomin `participant-grants.ts:95`, `guests.ts:883`, and the grant route in `live-contributions.ts`. The plan correctly identifies the stage read/increment/write race. A second race exists: `setParticipantGrant` builds a complete nested grant map from previously loaded metadata, then replaces that map. Two moderators changing different grants can lose one update; a stale write can restore a revoked microphone permission. The stage admission query and subsequent write also lack an atomic boundary with revocation.

   Correction: cover stage, grants, admission, expiry, revoke and producer reclaim in the coordinated mutation contract. Use atomic nested-key updates or revision checks where appropriate, and transact the durable policy/outbox changes. Preserve the existing contribution clocks and ledger. LiveKit token issuance must read the accepted current policy, not a stale route snapshot.

   Required proof: concurrent grant toggles, stage-versus-revoke, token-issuance-versus-revoke, retried command IDs and provider timeout/restart. Assert both final durable policy and provider enforcement; a successful local UI response is insufficient.

3. **P1 — PlatformAudio helpers cannot establish effective software AEC. Confirmed upstream wrapper limitation.** Plan §7, lines 142–144, and diagnostics §13. In the cited commit and the inspected `livekit/v0.9.4` tag, `active_aec_type()` chooses hardware versus software from hardware availability without checking enabled state. `set_echo_cancellation()` only invokes the hardware toggle when hardware is available; on desktop it can return success without toggling software AEC. The inspected `configure_audio_processing()` likewise configures hardware effects and logs the requested options. This does not prove that software processing is absent; it means these methods cannot prove its effective configuration.

   Correction: retain manual APM as the preferred spike. If comparing PlatformAudio, inspect the underlying software processing path and independently verify configuration changes and processed PCM. Do not use the status helper or success return as an AEC acceptance signal.

   Required proof: a controlled reference/microphone fixture with processing enabled and disabled, followed by actual speakerphone and double-talk measurements. Source: [PlatformAudio at the release tag](https://github.com/livekit/rust-sdks/blob/livekit/v0.9.4/livekit/src/platform_audio/mod.rs).

4. **P1 — Private cue needs an explicit host-mic destination interlock. Architectural risk.** Plan §5, lines 79–81, and §7, lines 126–138. Separate rooms enforce remote membership privacy, but the proposed common host audio publication creates a second boundary: the same processed physical microphone feeds public and private destinations. If private talkback only adds a private publication, public guests still hear it. Queued public microphone samples can also survive a destination switch. Private guest playback through host speakers may be acoustically recaptured; AEC attenuation is not an authorization boundary or a guarantee of zero leakage.

   Correction: specify an exclusive talkback destination state and sample-boundary switching, with public mic gating and stale-queue rejection. Define whether strict cue privacy permits speaker playback while the public host mic remains live, and qualify that policy explicitly. Music can remain separately routed. Include transport failure during the handoff.

   Required proof: recognizable private speech markers absent from public RTC and recordings through cue entry/exit, failed transitions, APM degradation and reconnect. Test both direct routing and physical speaker pickup.

5. **P2 — Native APM availability is narrowed to release-tag evidence, not packaged acceptance. Unknown integration.** Plan §7, lines 130–140. Verified `process_stream`, `process_reverse_stream` and `set_stream_delay_ms` in both the supplied commit and the `livekit/v0.9.4` tag. The public native export exists at the supplied commit. This supports the manual prototype, but does not pin the shipped crate graph or prove linking, device timing, thread ownership or real speaker-reference access. Current `program_audio.rs` taps audience/stage buses; neither is the final speaker-device mix.

   Correction: pin the selected crate versions, features, native binary provenance and lockfile. Include signaling TLS explicitly; the inspected LiveKit Cargo features state that WebSocket TLS is not enabled by default. Freeze the single audio owner, final playback tap, delay estimate, 10 ms framing and filter placement before broader integration.

   Required proof: packaged Apple Silicon and Windows builds, complete playback-reference coverage including monitored media/private audio, no duplicate capture/playback, device changes and measured AEC. Source: [release-tag APM](https://github.com/livekit/rust-sdks/blob/livekit/v0.9.4/libwebrtc/src/native/apm.rs), [release-tag Cargo features](https://github.com/livekit/rust-sdks/blob/livekit/v0.9.4/livekit/Cargo.toml).

The Cloud token replay concern is correctly called out. Official documentation describes a default revocation buffer that can admit recently refreshed tokens and recommends explicit `revoke_token_ts` for strict removal. Test the cutoff comparison and same-second behavior; apply retirement to old host identities as well as kicked guests. Backend epoch rejection alone cannot stop an already authorized provider publication. [Token lifecycle](https://docs.livekit.io/frontends/reference/tokens-grants/).

Remaining proof obligations: actual Worker token/RPC/raw-body webhook compatibility; provider operations that finish out of order; stale host reconnect after reclaim; private-room handoff with owned capture; raw/pre-encoded codec and hardware behavior; source/filter retention and rollback after new persisted state. The API has `nodejs_compat`, which is useful context but does not establish server SDK compatibility. Desired/applied reconciliation must measure enforcement lag when an obsolete provider operation finishes after a newer command.

Physical devices or WAN tests are required for speaker-reference delay and completeness, echo attenuation, double-talk intelligibility, Bluetooth/device changes, browser autoplay/background recovery, carrier switching, forced relay and TLS-only fallback, true capture-to-playout latency, thermal behavior and five-hour stability. Source review cannot establish any of these results. Synthetic room loads can establish transport/control capacity; they cannot qualify hundreds of native compositor/AEC sessions. Signed installer and updater acceptance remains a separate release gate.
