**Speakerphone audio contract — proposed, 2026-10-09.** Guests should be able to join on ordinary phone or laptop speakers without requiring headphones. This defines implementation and acceptance requirements for the guest transport refactor. It is not a shipped fix or a report of successful live tests.

**Keep conversation full duplex.** Each person's microphone remains available while others speak. Exclude their own voice from their playback, remove duplicate routes, and cancel acoustic speaker pickup before publishing microphone audio. Automatically muting microphones whenever another participant speaks would interrupt conversation and is not the intended solution.

**Route sources by identity.** Let H be the processed host microphone, M the intentional media audio, and G_i an authorized guest microphone. The audience mix is H + M + all authorized G_i. Guest i hears H + M + the other authorized G_j, excluding G_i. The host hears authorized guest voices once, with local microphone monitoring disabled by default. Apply current stage, cue and mute permissions to each destination.

In the proposed SFU path, publish host/media return audio without any guest voices. Deliver other guest microphones as separate authorized subscriptions. Do not subscribe a guest to their own published microphone. Keep program video and self-preview muted. Never play both a full program mix containing guest voices and independent guest tracks. A receive-only audience monitor must relinquish full program audio before gaining a publishing microphone.

**Own capture and playback explicitly.** Each physical microphone has one capture owner, and each remote track has one audible playback owner per destination. A processed native host microphone must feed production and RTC publication from the same capture path. If SDK playout owns guest playback, disable overlapping OBS monitoring; if OBS owns playback, do not also enable SDK autoplay. Track replacement, reconnection and stage changes must retire old players and reject callbacks from obsolete connection generations. Multiple microphones or colocated devices require an explicit selection policy.

**Cancel acoustic echo at every speaking endpoint.** Browser guests already request echo cancellation, noise suppression and automatic gain control in GuestJoinPage and GuestRoomPage. Preserve browser/SDK-compatible playout and record the resulting track settings; a requested setting does not establish measured effectiveness. The browser specification describes the scope of echo cancellation, including incoming WebRTC audio. [Media capture specification](https://www.w3.org/TR/mediacapture-streams/).

The inspected native integration creates OBS CoreAudio/WASAPI microphone sources and monitors guest audio through OBS. No explicit microphone AEC path supplied with actual speaker playback was found in that integration. A possible echo route is guest A → host speakers → host microphone → host/media return → guest A. Excluding guest tracks from the return bus does not remove that acoustically recaptured voice. This is a candidate failure mechanism, not a diagnosis from a recorded live call.

The preferred native prototype uses custom OBS-compatible capture with explicit WebRTC audio processing; SDK-managed capture/playout is an optional comparison. Requested settings and PlatformAudio status/toggle helpers do not establish effective software AEC or processing of external OBS microphone PCM. Independently inspect the processing path and compare enabled/disabled processed PCM, then measure actual speakerphone and double-talk behavior. The [October 9 review](./LIVEKIT-GUEST-REFACTOR-REVIEW-2026-10-09.md) records the helper limitations. [Release-tag PlatformAudio](https://github.com/livekit/rust-sdks/blob/livekit/v0.9.4/livekit/src/platform_audio/mod.rs).

For custom capture, supply the audio actually sent to the selected speakers as the AEC reference, with playback/capture delay accounted for. Include monitored media as well as conversation/private playback. Process microphone audio before production effects and publication; preserve intentional media audio separately. Reset or reconfigure processing when devices and routes change. The required Rust APM methods were verified at `livekit/v0.9.4`; selected crate/features/lockfile, native linking, real speaker-reference wiring and packaged acceptance remain unproven. The [implementation plan](./LIVEKIT-GUEST-REFACTOR-PLAN.md) requires explicit signaling TLS and one frozen capture/playback/reference owner. [Release-tag APM](https://github.com/livekit/rust-sdks/blob/livekit/v0.9.4/libwebrtc/src/native/apm.rs).

**Switch private talkback destinations explicitly.** Host mic has one effective destination: public, the named private admission, or muted. Switch through muted at a sample boundary, advance a routing generation and reject/flush obsolete samples and publications. Private talkback gates host mic from both public RTC and audience/recording; intentional media routing stays separate. Failed handoff or reconnect cannot automatically expose the private mic publicly. AEC does not enforce acoustic privacy: public mic must remain gated during private speaker playback and its measured output/acoustic tail, or private listening must use an isolated route. Test private speech markers against public RTC and recordings, including failed switches, APM degradation and physical speaker pickup.

**Expose evidence.** Diagnostics should identify microphone and output ownership, playback count per source, active return type, requested/effective capture settings and AEC reference availability. Do not label AEC verified based on a checkbox. Record route changes and recovery outcomes without logging credentials or private signaling payloads.

**Release acceptance.** Routing tests must establish zero digital self-return, one playback route per remote voice, and a complete audience mix. Acoustic tests must separately measure residual echo during remote-only speech and speech preservation while both sides talk. Compare processing enabled and disabled on the same devices and record actual output levels.

Test one native host and three browser guests on speakers, including Safari/iPhone, Chrome/Android and desktop browsers, against supported native host builds. Exercise simultaneous speech, music, mute, stage promotion/demotion, device changes, Bluetooth changes and reconnection. Include a five-hour session matching the proposed usage model. Predeclare acoustic and intelligibility thresholds before evaluating results. Do not claim speakerphone readiness until the measured matrix passes; current inspection performed no such live acceptance test.
