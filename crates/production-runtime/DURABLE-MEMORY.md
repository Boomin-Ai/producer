# Durable document memory qualification

This slice runs only in `crates/production-runtime`. It does not open Producer profiles, cameras, files from a user library, native renderers or a GPUI window. The JSON document/command schema and numeric animation callback remain unchanged.

## Snapshot ownership

Document root collections use `SharedMap<T>`, a wire-transparent `Arc<BTreeMap<String, T>>`. Cloning a document shares its immutable maps. A mutable map borrow detaches that map through `Arc::make_mut` before mutation; other versions and held inspections retain their original values. This is coarse map-level copy-on-write, not a persistent tree down to every node. Editing one Set still copies its containing Set map when it is shared. Deserialized JSON remains an ordinary object; no pointers, native handles or sharing IDs appear in the authored document.

Undo is bounded by all three dimensions per document: 16 entries, 32 MiB serialized bytes and 2,097,152 structural units. A unit is one JSON value/container or object key. The byte/unit counts are streamed without materializing another JSON tree. They are conservative retention dimensions, not allocator or resident-memory estimates. Large documents have a shorter undo horizon. Shared backing storage is deliberately charged again for each retained version; deduplication does not grant extra undo capacity.

Canonical hashing streams the existing JCS encoding into SHA-256. Serializer-owned bytes are traversed through borrowed raw values instead of constructing another full JSON value tree. Object keys still allocate for UTF-16 ordering; this is not zero-allocation admission. The same strict ingress visitor can discard values for validation, retaining duplicate-key detection without retaining a second tree. RFC number/key ordering, prefix and digest identity stay unchanged. Tests compare against the prior Value-based oracle, including f32 widening, numeric/string keys, nonfinite values, enums and custom serializer duplicates. The borrowed-value dependency feature has a private sentinel key; metadata uses the ordinary bounded visitor so such keys remain literal, including during checkpoint recovery.

The document coordinator and FileStore each own a reusable wire buffer capped at 48 MiB. Startup validation transfers its buffer into the FileStore. Command preflight, document validation/hash, compilation, prospective checkpoint admission and observer hashing reuse the coordinator buffer. Receipt-size accounting streams to a counter. Compilation still performs complete semantic admission; only a redundant validation immediately before that same compile was removed. No validation, checksum or pre-append check was bypassed. A successful serialization keeps bounded headroom to avoid a late resize as receipt history crosses an allocation boundary. Neither buffer is global, thread-local or retained after its owner drops.

The process host separately reserves 96 MiB of writer scratch per admitted document (192 MiB for two), in addition to its encoded-retention/wire/read allowances. This conservative reservation is not an allocation or an RSS cap. The near-limit workloads actually retain four 9 MiB buffers across two coordinators/stores: deliberately more bounded live scratch in exchange for less repeated large allocation churn. Other candidate objects, key collections, recovery decoding, native pools and allocator overhead remain separate.

A successful save moves the previous document into history, rather than cloning it again. All fallible history measurement happens before the append. Eviction/consumption happens only after a known durable result. Known-not-written and uncertain saves cannot evict or consume previous history. Undo remains a new revision naming the exact current history entry. Undo is current-session history, not persisted across restart.

Authenticated native callers can request lightweight `history_status`; CLI `inspect` includes the same count, byte/unit usage and limits. This does not require a document copy just to inspect accounting. Held inspections still consume the existing four-reader/64 MiB encoded reservation pool even when their immutable maps share storage.

## Store admission

Document ingress still caps work at 1,048,576 values, 8 MiB encoded bytes and depth 32. A transport/checkpoint envelope has an additional 65,536 value units and eight depth levels, to fit one maximum-work document plus the existing bounded receipt history. The embedded authored document must independently pass the original document limits. Increasing wrapper headroom does not raise the document budget.

Loaded checkpoints, native host factories and checkpoint writes enforce the existing receipt profile: 4,096 records, 16 MiB aggregate encoded history and 64 KiB per receipt. A store cannot admit oversized receipt history and defer pruning until its next mutation.

## Reproducible workload

Build the release `durable_memory_proof` example and run `scripts/prove-durable-memory.py`. The script runs all three independent processes and preserves exit status, output and errors, including failed memory gates. The core CI matrix includes it, with artifacts uploaded on failure; remote execution is not implied by the workflow file.

- Byte-heavy documents: two documents within 4 KiB of the 8 MiB ceiling, repeated small durable title edits, actual sync/checkpoints, close, reopen and historical ticket retry.
- Dense-value documents: two documents near both the byte ceiling and the raw-value ceiling. The shape intentionally exercises much more Rust object overhead per encoded byte than text-heavy documents.
- Journal pressure: repeated near-8 MiB imports until the real 64 MiB journal cap rejects. The test does not fill the physical drive. It checks unchanged revision/history, identical retry rejection, checkpoint reclamation, a fresh successful ticket, reopen/replay and historical receipt reuse.

Each two-document process applies 48 durable edits, checkpoints every eight edits per document, samples heap/RSS every four rounds and retains four admitted read leases across exact close. A fifth read rejects. Read capacity returns only when those leases drop. Stale submit handles cannot retain the writer lock or author again. All temporary files live in a unique experimental directory and are removed by its owner; the proof caps its files below 192 MiB and requires space for existing checkpoint reserves.

The requested-heap instrument wraps the test process's Rust system allocator, including transient peaks. RSS samples use self-process Mach task information on macOS or `/proc/self/statm` on Linux. Windows RSS sampling remains unimplemented. Neither instrument measures GPU residency, external allocator internals, native media pools or application responsiveness. Allocator caching/fragmentation can make RSS differ substantially from live requested bytes.

Local plateau gates use the last four periodic samples: less than 1 MiB requested-heap span and less than 64 MiB RSS span when RSS is available. After host/read release, retained requested heap must be within 1 MiB of baseline; small proof-owned measurement records are still alive. No allocator purge or system memory-pressure call is used. The local tool environment inherits `MallocNanoZone=0`; the proof does not change allocator settings. This is part of the environment qualification, not a claim about the production app allocator.

## Evidence and limits

Historical source-linked attempts live in `evidence/durable-memory-profile.json`; every earlier failure remains with its original source identity. The first owned-map implementation completed 48 byte-heavy edits with stable requested heap but failed the RSS plateau gate twice. Shared immutable maps reduced retained document copies but did not resolve the later RSS failures. The subsequent bounded-admission work is recorded separately in `evidence/admission-memory-profile.json`, including failed intermediate attempts. Thresholds and workload were not relaxed.

These shapes qualify specific durable-writer ownership and retention paths. They are not an exhaustive maximum-node/track/receipt/source/native allocation matrix, long-duration leak proof, full filesystem power-loss test or controlled comparison against the production desktop. Native executor/socket ingress, physical media/GPU disposal and platform results remain separate gates.

The earlier self RSS result was cross-checked on macOS against `proc_pidinfo` and `getrusage`. A separate diagnostic VM map found substantial freed “Malloc Large (empty)” mappings and deferred reclamation. That observation motivated reducing temporary allocation churn; it was not proof of a sole cause or successful mitigation. Diagnostic VM inspection may perturb a process, so it is retained separately from normal profile attempts.

Historical [behavior checks](evidence/durable-memory-checks.json) retain the 158-test source and failed resident-memory qualification. Current verification and qualified workload identities are recorded in [admission checks](evidence/admission-checks.json), [memory attempts](evidence/admission-memory-profile.json) and [numeric/compile profiles](evidence/admission-core-profile.json). Current results do not relabel historical runs or qualify a native renderer, GPUI, long-duration leak behavior, repeated large-document recovery or a complete physical allocation matrix.

Final compatibility-corrected source: **165 tests / 16 verification steps pass**. Memory attempts 19–27 record three independent processes per shape: six large-document runs and three journal-pressure runs, all passing. The last four edit samples varied by **26,293 requested-heap bytes** and **212,992–17,399,808 resident bytes** (0.20–16.59 MiB), under the unchanged 1 MiB/64 MiB gates. No successful allocation/reallocation request of 1 MiB or larger occurred between the round-four sample and the last edit sample. Owner/read release, recovery and exactly-once local ticket reuse passed; all host reservations, including writer scratch, returned to zero.

With reusable buffers included, the final edit samples retained about **52.1 MiB requested heap** for the byte-heavy pair and **106.1 MiB** for the dense-value pair. After host/read release, proof-owned requested heap was 18,753 bytes versus a 727-byte baseline. RSS can remain elevated after release/recovery (these runs retained roughly 143–333 MiB at final sampling); the gate measures plateau variation during edits, not return of physical pages to the OS. These finite runs therefore do not prove an absolute resident limit or a leak-free 24-hour session. No allocator purge, tuning or sleep was used to obtain a pass.

Six fresh 1,000-node / 256-track / 256-held-override numeric/compile runs also passed. Numeric evaluation p99 was **0.007209–0.031542 ms**, Show numeric p99 **0.008333–0.066541 ms**, both with zero measured allocations. Cold compile was **13.29–16.92 ms**, dirty-layout p95 **13.47–13.65 ms**. These are core-only, uncontrolled-load observations, not a controlled A/B or desktop speedup. The six earlier pre-metadata-correction timing runs remain in `admission-core-profile-initial.json` with their original source identity.

## Recovery scratch and typed decoding

The later combined pressure workload also exercises repeated large checkpoints and replay. FileStore checks the complete raw envelope in discard mode before typed deserialization, then verifies the checksum using its retained scratch. Replay shares that same scratch for command admission, application, canonical outcome validation and retained receipt sizing. MemoryStore recovery uses one local scratch for its entire replay as well. Duplicate decoded keys, UTF-8, number/depth/work limits, literal metadata keys, strict fields, legacy Value-encoded checksums and fail-closed corrupt records remain required. This removes a duplicate full JSON tree and repeated scratch allocation; it does not waive validation or by itself qualify resident memory. See [combined qualification](PRESSURE-QUALIFICATION.md).
