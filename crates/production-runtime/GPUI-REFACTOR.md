# Producer native room studio and production engine plan

Decision date: 2026-11-15. GPUI is the selected desktop UI architecture. The target replaces Tauri and the React/webview application, and replaces Three.js/browser-authored Set rendering with a Rust-owned native graphics engine. The existing production core is retained and completed. This is the implementation plan, not a claim that the new desktop or renderer is built.

Producer is a live media production and distribution harness. Its room, Set engine, Show engine and Studio must work together: users and authorized agents can compose live inputs, run polished Shows, retain program and selected original footage, and edit available footage while capture continues. Boomin remains the collaborative brand/network service, not a model provider or the local rendering authority. Reference projects inform individual implementation choices; their product structure does not redefine Producer.

This plan supersedes the earlier reviewed plan's UI/renderer destination and dependent qualification steps, particularly D04, D09, D11 and Phases 2–4. Its authority, time, durability, admission, privacy and ownership rules still apply. The [implementation review ledger](REVIEW.md) records the scope of historical reviews; those reviews do not certify this later GPUI plan. Existing implementation evidence remains in [READINESS.md](READINESS.md); unchanged historical measurements must not be relabeled as GPUI or native-renderer results.

## Fixed product and architecture decisions

- **Native desktop:** GPUI owns windows, room panels/docks, menus, Assistant, Set Edit, Show controls and the timeline. GPUI Kit is optional reusable behavior/components, not Producer's visual identity. Use only needed features. Tauri is removed at qualified desktop cutover, not kept as a second long-term application framework.
- **Native production graphics:** Rust owns 2D/vector/text, compositing, 3D, effects and production animation. Three.js, JavaScript execution, DOM measurement and CEF are not required to render a Set. Optional browser-source support is a separately admitted input adapter if the product needs it; it is not the Set engine or a reason to retain Tauri.
- **One production runtime:** Sets, Shows, nested sequences, source placements, Studio camera moves and effect parameters share typed targets, time mapping, driver arbitration and resource ownership. GPUI interaction animations may have UI-local timing; they do not drive recorded production animation or fire Show cues.
- **One authoring contract:** versioned JSON remains portable authoring/interchange, with typed Rust/Serde models and generated schemas. Compile it into bounded runtime plans. UI, CLI, MCP and Assistant use the same validated operations; they do not exchange JSON or perform layout on the audio/video callback.
- **Protect working infrastructure:** reuse qualified capture, codec, audio, recording, LiveKit/network and virtual-camera code through adapters. Rust ownership does not require rewriting mature C/C++ codecs or every platform bridge. Existing Sets may be replaced; user media, accounts, library assets, credentials, permissions and network identities must survive cutover.
- **Shared performance budget:** an impressive Set/Show and a responsive editor are both product requirements. Neither an empty native shell nor an isolated GPU demo qualifies the refactor.

## What already exists and what must finish first

The isolated workspace has exact rational time, typed documents, scoped components and players, incremental compilation, commands/persistence, synthetic lifecycle/resource accounting, nested sequences, manual Show occurrences and headless CLI proofs. The current local evidence includes native graphics budget admission, compiled dependency lifetimes and source-aware production geometry; see the readiness ledger for executed counts. It has no GPUI dependency, actual renderer, capture, codec or audio output. The complete A01–A25 ledger is authoritative about the remaining work.

Complete the following contract work before broad native integration:

1. **Implemented in the logical model:** a compiled manifest replaces the symbolic Set resource with component/source/player/font/graphics/audio dependencies. Cycles, capacity, owner removal, transitive reads, dependency-ordered disposal and preparation reservation pins have regressions. Explicit source/bus route duplicates reject; inherited equal routes coalesce. Native allocation/callback/destruction wiring and compatible live Show plan handoff still require qualification. See [ownership contract](SHOW-OWNERSHIP.md).
2. **Implemented in the headless model:** anchors, pivots and explicit source-aspect constraints, required fallbacks, intrinsic row/column reflow, ties-even raster admission, immutable dimension inputs and preparation fences. [Geometry contract](LAYOUT-CONSTRAINTS.md) documents the tested scope. Native source dimension/incarnation discovery and font metrics remain separate adapter gates; GPUI layout cannot silently change production geometry.
3. **Implemented in the local control model:** [one process-owned host](PROCESS-HOST.md) shares session/observer/storage admission with the two-document lifecycle/compile workspace and deduplicates concurrent in-flight retries. Qualify its native single-owner/executor/ingress wiring and maximum-document/durable-writer memory before desktop adoption. The [durable memory slice](DURABLE-MEMORY.md) adds shared immutable document versions, adaptive undo and real file-store pressure proofs; bounded writer scratch and borrowed/discard admission now pass the tested local heap/RSS plateau cases. Earlier failures remain recorded; the [bounded control service](CONTROL-SERVICE.md) now qualifies the isolated single-owner/ingress boundary. A broader maximum-document/service/recovery/native allocation matrix remains an adoption gate.
4. **Implemented in the core input model:** explicit versioned analytic seeds, scope and exact content clocks; incremental commands, nested reconstruction, seek/restart and independent SHA/Fraction oracles. [Reconstruction inputs](ANALYTIC-RECONSTRUCTION.md) are allocation-profiled separately from numeric tracks. Native Set clock binding, GPU upload/kernels and renderer equality remain required. Keep stateful simulation unsupported until bounded checkpoint/replay is qualified.
5. **Implemented in the synthetic model:** graphics now reserve typed native scenes, pipelines, passes, textures, buffers and instances instead of browser contexts. Checked admission and retained uncertain/retiring charges are covered by local regressions. The all-layout preparation profile charges additional targets for paired views and assumes no asset sharing. Remaining native work: probe actual allocation bytes and lowered graph expansion, qualify warm/preview residency and sharing, and acknowledge destruction on the correct GPU lane. This model does not render or establish physical GPU capacity. See [current evidence](READINESS.md#native-graphics-accounting-slice).
6. Run core platform CI, broaden crash/fuzz coverage, retain source-linked results and review the later slices. Passing local model tests does not satisfy native gates.

These are bounded core jobs. Do not add GPUI, FFmpeg, a game engine or GPU types to `contract` or `core` to finish them.

## Runtime boundaries

| Boundary | Owner and responsibilities |
| --- | --- |
| Production document and commands | Rust contract/core: document revisions, components, Sets, Show definitions, sequences, validation, permissions and durable authoring. |
| Workspace | Separate Rust workspace state: panel/dock arrangement, selection, editor scroll/zoom and operator presentation. Moving a panel does not rebuild the media graph. |
| Production execution | Rust runtime: compiled plans, transport domains, active Show/segment occurrences, cues, takes, overrides and resource admission. Hosted fields remain projections of their actual server authority. |
| Native media | Capture/decode/audio/record adapters: timestamped samples and frames, probes, controller leases, device recovery and correct-thread disposal. |
| Native renderer | GPU device/context ownership, retained resources, text/vector/3D passes, masks/effects and immutable output frames with readiness/retirement fences. |
| GPUI desktop | Input, accessible native controls, rendering of room/editor state, presentation of GPU output, and operator-only authoring surfaces. It is not the recorder or production clock. |
| Distribution and integrations | Existing authorized services for streams, guests, Boomin, provider jobs and publishing. Transport retries cannot invent local or hosted authority. |

Intended flow: agent/operator command → validated durable document → off-callback compile/prepare → timestamped runtime evaluation → native media/graphics/audio → program frames/samples → preview, recording, stream, virtual camera or guest output. A display stall cannot become the production clock. Read-only observers expose the state of each stage separately.

Names above describe boundaries, not a demand to create an empty crate for each. Extract existing implementations behind narrow interfaces as a working slice requires them. In-process typed calls are preferred inside the desktop; CLI/MCP use authenticated bounded IPC against the same operation catalog.

## Set and Show engine requirements

The Set engine is a retained, composable scene system, not a collection of hand-painted screens. A reusable component declares pinned definition/assets, typed props, ports, state authority, native visual tree, actions, motion targets and control presentation. Instances isolate mutable state; immutable geometry, textures, fonts and pipelines may be shared under compatible device/configuration keys. Native component recipes and bounded effects are the first authoring vocabulary. Agents do not need to generate or compile Rust for ordinary design work.

The first useful native vocabulary includes source/video surfaces, text and vector paths, images/SVG, crop/fit/masks/feathering, groups, themes, layouts, cards/lower thirds/CTA overlays, native control groups, and timeline-driven properties. Richer native 3D adds instanced geometry, materials, lights, camera projection and admitted shader effects. Prewarm pipelines; avoid rebuilding meshes, text layouts or entire render targets for a button click. Native GPU access supplies primitives, not a ready-made replacement for Three.js: asset loading, material behavior, scene evaluation, typography and quality all need implementation and qualification.

Set layouts have independently authored landscape/portrait compositions with shared semantic state and tokens. A source metadata change invalidates affected layout dependencies only. Layout switching is prepare/revalidate/frame-boundary take; a compatible edit retains source/player identity and warm resources. Failed preparation retains current output and returns structured diagnostics visible to the Assistant. A Set must work without a Show.

The Show engine references Set layouts, sequences and supported cues in ordered segments. Show definitions, run identities and segment occurrences remain distinct. Add timed advancement, manual holds, transition handles, media-completion conditions and authorized guest/moderation actions in explicitly versioned capabilities; the current core proves manual navigation only. Every asynchronous completion binds the run/occurrence/transport/resource generation. Manual next, stop, replay and reentry must not double-fire sounds, guest actions or external effects. Prewarm the next admitted segment without exceeding the combined live/incoming/retiring budget.

Reusable transitions are timeline components with named inputs/outputs and explicit audio behavior. Topic/CTA overlays are separately callable actions; they must not replace the segment stinger or accidentally navigate to a layout. Answer selection, correct/wrong/trick reveals, native border/glow effects and sounds are ordinary typed component state/actions, not special-case application code for one Show.

Live controls remain designable: per-layout/segment controls first by default, then global Set controls, unless explicitly arranged otherwise. Support compact/equal-width/primary/selected semantics, sliders, conditional visibility, source/guest/data controls, and distinct compact side/top/bottom forms. Content and appearance editors stay behind Set Edit. Empty sections disappear. Native header/transport colors remain Producer UI colors; authored tokens style the content/control surface. No repeated decorative frames or mandatory cutout/background fieldset. Guest placeholders may expose an authorized invite action rather than a dead card.

Classic is the first polished production fixture: eight layouts in both orientations, equally intentional dark/light themes, camera/screen/media, live controls and sound cues. Pilot follows as an actual Show with timed/manual segments and transitions. Both must be authored through the real Assistant/CLI, not generated by privileged code that bypasses the public contract. Design quality and interaction at each dock size are acceptance work, not automatically provided by GPUI Kit.

## Live footage and editing while recording

Keep three objects distinct: a live source, an immutable recorded asset, and a timestamped take connecting recorded ranges to the source/clock/format generations that produced them. A clip is a timed use of a source/player/component; a track/lane is an editing projection, not another media owner. Spatial order and temporal tracks are separate concepts. A component may contain nested visual layers and sequences without forcing every leaf into the top-level timeline.

Recording modes are explicit: program only, or program plus selected original inputs/isolated audio routes. The target includes both flattened program and originals; original capture is not an accidental always-on recording of every guest or device. Reuse timestamped capture samples where possible, charge every additional encoder/writer, and retain existing user permission and recording indicators.

Write append-only chunks/segments and publish a versioned take manifest with durable seekable watermarks, media time bases, source identity, A/V offsets, format/discontinuity markers and ready ranges. Readers open committed ranges, not a partially written monolithic MOV that is presumed seekable. Finalization joins/indexes the take without changing earlier source identity. Disk full, removal and writer stalls must publish explicit status and preserve playable committed ranges. Do not silently fall back from an unavailable external drive.

A live source cannot be scrubbed backward unless its footage exists in an authorized rolling buffer or take. A program frame cannot recover its flattened original layers. Cutting the recorded original uses a separate player/controller from live capture. Cutting the program edits the flattened recorded view. Each can continue growing while capture writes later chunks. Short clips, 24-hour takes, variable frame rate and disconnected/replaced devices use the same exact range and generation rules.

Separate the continuous live output clock from seekable edit/rehearsal transport. The Assistant can cut a growing take, change a private composition and prepare it while the current program keeps running. Taking that candidate is explicit unless the host has already granted that live-operation scope. Seek/replay never repeats network posts, sounds or guest admission actions. The UI and Assistant can inspect available ranges and recording lag; neither invents future frames.

## Native GPU and visual fidelity

Use `wgpu` as the initial common native graphics API candidate behind Producer's renderer boundary, with native Metal/D3D/Vulkan bridges where required for media interop. The precise pinned GPU and GPUI backend versions are selected in the interop proof, not by adding several incompatible GPU devices now. GPUI is decided; upstream versus GPUI Fast is a narrow implementation/compatibility choice under the same product architecture. Start the comparison with the same representative room, not a component-gallery benchmark. There is one selected backend in a shipped binary.

Prefer GPUI primitives/custom paint for the application. Evaluate needed GPUI Kit Base behavior and components individually, with default/extension features disabled when unused. Use Taffy through the chosen UI stack for UI layout; output geometry continues to come from the production layout contract. `resvg`/vector paths, a qualified text shaper/font stack and a 2D renderer such as the appropriate Vello family are candidates where they remove needed work. They are not an instruction to install a full stack. Do not add Bevy or another full application scheduler merely to obtain a rendering feature. `gpui-motion` can inform interruptible UI feedback, but cannot become the production animation clock.

Prove interop explicitly: GPUI, the production renderer, decoders/capture, compositor and encoders may use different devices/APIs. Same GPU vendor does not imply shared texture ownership. The bridge must describe native handle/format/plane/stride, device and context generation, acquire/release synchronization, actual copy count, readiness and disposal lane. GPU-to-GPU copies may be the honest supported path; zero-copy is advertised only with physical evidence. Never use GPU readback → CPU image → GPU upload as the default live preview architecture. Cross-adapter Windows and integrated/discrete GPU changes require explicit rejection or a measured supported transfer path.

Vector paths, SVG and text remain resolution-aware. Cache text shaping by pinned fonts/style/content; shape/layout changes off callback. Render at admitted output density and maximum planned zoom, not the small UI preview dimensions. Antialias transparent perspective boundaries, maintain alpha and explicit SDR color/transfer conventions, and use the same compiled scene/effect semantics for preview/record/export. Export quality never inherits a reduced preview raster. Finite camera/window pixels cannot supply unlimited zoom detail. HDR and expensive filters remain unavailable until qualified; no silent quality drop when Studio activates.

Retain scene graphs, immutable GPU resources and frame plans. Apply compact dirty-range/uniform updates; batch compatible geometry, cull invisible work, use bounded atlases and explicit pass/overdraw/shadow/postprocess budgets. A paired layout shares suitable source reads and state but still costs two projections/renders. Analytic effects sample supplied time and seed; stateful effects need bounded checkpoint/replay or an explicitly live-only capability. Music-reactive reproduction requires recorded audio/features, not a new wall-clock animation loop.

The former 10× Three.js goal becomes a native visual-capacity experiment: compare fixed-quality workloads of repeated instances, unique materials, vector/text detail, transitions and live dual output against released 0.4.93. Record workload changes, CPU/GPU tails, frame age, memory and recording results. Do not turn an object-count increase or a fast core-only evaluation into a universal 10× performance claim.

## Room and Studio on GPUI

The room keeps the existing fast workflows: instant navigation feedback, retained dashboard/library state, reliable camera/mic/guest/source recovery, distinct active/prepared/private state, compact icon toolbar, native tooltips and anchored opaque sheets. Host/guest mixer routing is independent of visual layout membership. Rebuilding the UI must not recreate device/stream keys or change Boomin's host/network leases.

Studio uses the room's existing canvas for preview. The timeline is a native panel permitted in top/bottom docks and an optional separate bottom Studio bar. No side timeline, duplicate preview or required popout composer. Selection populates motion parameters in the same bottom surface; deselection removes those parameters. Retain source/motion handles, continuous extension and edge scrolling. The one-minute limit belongs to the existing Studio motion composition profile, not to source take length or the future editorial timeline.

Panel, window and canvas are supported target categories to qualify. Production composition targets render directly from the output graph. Native panel/window targets require either a qualified read-only GPUI paint/render-target path or platform capture; an OS child surface alone does not establish offscreen/recording support. Lifted views share observed state and approved geometry but cannot create another writable widget/transport authority. High-density text rendering, perspective sampling, frame tags and transparent clipping are required. Composer controls stay out of a separate-bar recording; a docked Timeline is included only by the chosen capture policy. Check for recursive preview/capture dependencies before activation.

GPUI owns accessibility, focus/IME, clipboard, drag/drop, file dialogs and panel interaction. A small Rust platform-services facade replaces the Tauri services actually used: app lifecycle, OAuth loopback/deep links, secure storage, preferences/assets, diagnostics, notifications, updater, signing/entitlements and virtual-camera lifecycle. Inventory each service before deleting its old path. Browser-based ChatGPT/provider authorization can still use the system browser; that is not a Tauri UI requirement.

## Assistant MCP and component authoring

Expose one capability/operation registry, including exact support/permission status, resource limits, current diagnostics, document selection, private draft base, source ready ranges, take manifests and prepared/active revisions. Clean Assistant context follows current room selection; an edited draft is explicitly pinned and cannot silently overwrite another Set. Bugs can be reported from structured failures through the existing authorized report flow, with review/redaction boundaries intact.

Agents can incrementally author component instances, themes, controls, paired layouts, Shows/segments, cue bindings, timeline placements and Studio motions. Validate and prepare them through the same path as user edits. Attachments declare inspiration versus production asset intent. A referenced website/library example is a pinned recipe with known capabilities, not executable code or blanket filesystem/network authority. Keep model providers and generation adapters replaceable; Boomin is not a generation provider.

Use reusable manifests and examples for great authoring: native control semantics, spacing/font/color tokens, source placeholders, guest invite states, empty/error/loading states, actions, motion recipes, output/dock variants and cost/capability declarations. Start with small composable libraries; do not import a giant collection or execute arbitrary generated shader/native code in the live process. Custom shader/import extensions need separate validation, compile isolation, timeout/resource limits and a qualification profile before advertising support.

## Performance and adversarial gates

Freeze workload manifests and thresholds before running the new implementations. Retain the existing core p99/compile/allocation targets and reported limitations. At 60 fps, each output has a 16.67 ms frame interval; at 30 fps, 33.33 ms. Those are deadlines, not a claim that the compositor owns the whole interval. Budget evaluation, source preparation, compositing, transfer and encoder work separately. Record input-to-feedback and input-to-correct-frame latency separately from average FPS.

Required workloads include idle cards/room, a camera/mic Set, paired 1080p output, a rich native Set, a four-guest Show, rapid layout/cue changes, long-take waveform scrolling, growing-take scrubbing and concurrent recording/Studio motion. Measure cold/warm first frames/audio, p50/p95/p99 CPU/GPU times, missed deadlines, frame age, copy/upload bytes, audio underruns, device recovery and memory plateau. Background analysis/thumbnail/proxy work yields to live output and uses bounded workers/queues. Available recording ranges advance only after the matching storage/durability state.

Before native adoption, retain counterexamples for: late decode after seek/close/reopen; stale Show completion; missing guest/screen recovery; duplicated audio from two orientations; superseded prepared layouts; queue saturation with stop/revoke; GPU loss during recording; incompatible texture device; private UI leaking into Studio/model context; partial take writes; external-drive failure; a 24-hour take with bounded metadata/cache memory; and edits to an original accidentally seeking the live source. Unsupported features reject before live adoption and preserve the current program.

This plan has parent review against those cases, not a new independent adversarial closure. No absolute no-regression or 10× promise follows from the framework decision.

## Reference decisions

- [GPUI Kit](https://github.com/longbridge/gpui-kit): optional component/base behavior and current Fast selection support; use minimal features and pin a coherent dependency graph. Its current README documents both upstream and Fast choices; compatibility is verified at the chosen revision.
- [GPUI Fast](https://github.com/longbridge/gpui-fast): retained layout/paint and native surface/dynamic-texture work inform N2. Gallery benchmark results are not Producer performance evidence.
- [OpenCut](https://github.com/waterblower/opencut), inspected at `fe6cabbc3344478155ae1af35596811ee8ba80d3`: take ruler/zoom/snap/trim/visible-range waveform lessons. Do not import synchronous UI decoding/saves, process-exiting playback errors or unbounded reader caches. Resolve licensing before copying code/assets.
- [gpui-motion](https://github.com/1bye/gpui-motion): UI-motion reference only; backend compatibility and exact dependency versions need verification. [Zeron](https://github.com/zeronsh/zeron): native agent-UI reference, not Producer's media pipeline or product architecture.
- [wgpu](https://github.com/gfx-rs/wgpu): initial native GPU API candidate. Native API support is not proof of decoder/GPUI/encoder texture interop. [Vello](https://github.com/linebender/vello): evaluate the specific 2D renderer family/maturity against our workload rather than treating every Vello crate as one production-ready renderer.

No dependency from this list is added by the plan. No production desktop, app profile, native engine lock, backend or release changes as a result of recording the decision.
